# TagForge 2.0.0 优化与发布计划

制定日期：2026-10-09。基线：当前工作区，包版本 0.1.13，包含已有未提交修改。

当前状态：2026-10-09，本地 2.0.0 修复、验收和最终安装包准备已完成，尚未正式发布。最终证据见 [验收清单](../../RELEASE_READINESS.md) 和 [release.json](../../../tests/validation/release.json)。下文保留原范围与基线，文末记录最终状态。

## 目标与范围

2.0.0 的目标是让现有流程的结果、重跑行为、配置和输出形成稳定约定。发布前先完成基础修复及必要验证，不把所有算法探索和性能重构都作为发布条件。

当前保留三类用途：普通 Barcode1–feature 文库、PI-seq、PB–CB。原始全深度计数是主结果；降采样是分析与诊断结果。多段提取、纠错 trace、UMI-tools 去重、Slurm 和批次汇总继续支持。

本文件定义实施范围与验收条件，实际进度见 [实施记录](TagForge_2.0.0_progress.md)。既有工作区修改应先审阅并形成开发基线，避免将未审阅的修改直接混入发布。

## 已有证据与限制

- 已验证 23 个单元测试及 1 个端到端集成测试；现有覆盖仍不足以证明边界正确性和纠错准确率。
- 随机 PI-seq 子集 `100-1-N1` 的 50,000 对 reads 跑通：47,281 有效 reads，46,423 去重分子，PI-seq 过滤后 46,413 分子。
- 该子集全深度 sequencing saturation 为 1.815066%；这不是原始完整样本的饱和度评估。
- 已复现 quick-test 与正式流程在部分片段失败时判定不同、全深度选择后旧 optimal summary 残留、零记录 fragment dataset 无有效文件、原位置 exact 命中后继续执行错配搜索。
- 真实子集 PB2/PB3/PB4 分别存在 3,823/4,108/4,276 次“最短间隔长度错误，但另一候选符合长度且精确命中白名单”。这是分段计数，存在 read 重叠；候选命中不能直接当作真实定位正确。

## M0：冻结基线与分析约定

1. 审阅当前未提交变更，区分已实现功能、修复和 fixture 调整，形成可追踪开发基线；保存代码标识、规范化配置及依赖版本。
2. 将现有合成数据和四个 PI-seq fixture 的参考结果保存为独立基线。运行所有样本，记录各阶段 reads、分子数、矩阵计数、耗时和峰值内存。
3. 新增带已知真实标签的合成 fixture：多个片段、提取失败、重复 linker、移位、错配歧义、N、UMI 邻居、PI 多 PB、PB–CB alias 与共享 UMI。真实 fixture 用于检查分布及差异，合成真值用于评估纠错错误。
4. 定义流程过滤链：输入 reads → 全段提取成功 → barcode 合格 → feature 注释合格 → UMI 合格 → 去重 → 文库过滤。每个指标明确分母与计数单位。
5. 固定指标约定：
   - `sequencing_saturation = (eligible_reads - detected_molecules) / eligible_reads`，与相同分组及 eligible reads 下的 duplication ratio 数值相同。
   - `non_singleton_molecule_fraction` 是观测分子中支持数大于 1 的比例，不作为最佳测序深度的已验证定义。
   - 当前降采样采用全深度纠错后固定分子组的支持 reads 抽样，不宣称每个深度都重跑了完整纠错流程。

验收：基线可以重复生成；指标在日志、TSV、JSON、Excel、HTML 中有相同解释；新增失败用例能够稳定复现问题。

## M1：重跑、检查点与产物一致性

### F01：阶段指纹与依赖失效

- 完成 manifest 保存阶段相关的规范化配置、算法/schema 版本、直接输入产物标识、依赖文件指纹、输出清单和行数；程序及依赖版本作为审计信息记录。
- 小型白名单、annotation 采用内容摘要。大型 FASTQ 默认记录路径、大小和高精度修改时间；明确这属于元数据校验，并提供可选内容摘要。Parquet dataset 必须枚举实际 fragment，不能只对目录做 `stat()`。
- 修改一个参数，只使受影响的阶段及其下游失效。修改报告样式不重新计算 FASTQ，修改白名单必须重新纠错并更新后续结果。
- 独立阶段命令运行前验证输入完整性；重跑上游后，汇总不得继续展示已失效的下游数据。
- 旧版仅记录程序版本的 `.done` 不作为可信 2.0 完成状态，明确提示重算或执行经过验证的迁移。

验收：分别改变白名单、annotation、提取坐标、UMI 参数、降采样 seed，检查重新执行的阶段；改变线程数不得无理由改变计数；单独重跑上游后不会继续复用旧报告。

### F02：阶段发布与恢复的完整性

- 为同一样本增加互斥保护；保留已有跨样本汇总锁。不同样本仍可独立并行。
- 以工作目录/产物代次写入结果，通过原子发布完成 manifest 使结果对下游可见；禁止把正在生成的目录当成完成数据集。
- 批次恢复状态应保留到输出和完成状态发布成功；覆盖“最后一个批次写完但统计未写完”“产物完成但 `.done` 未发布”等故障窗口。
- 暂不要求 dedup、matrix、pair-map 都支持批次恢复；这些阶段必须能安全整步重算，并清楚报告恢复粒度。

验收：关键提交边界注入中断，恢复结果与干净运行一致；缺失或损坏 fragment 不能通过完成检查；同一样本并发运行不会混写。

### F03：降采样选择与旧产物清理

- 本次 manifest 明确引用 selected 数据集及其指标，不根据 optimal 文件是否存在选择来源。
- selected ratio 为 1 时允许引用本次全深度数据，无需复制整个明细；所有消费者通过统一接口解析引用。
- 每次重算使旧 selected/optimal 产物失效。比例、seed、repeat 改变后，明细、矩阵、汇总必须来自同一次选择。
- 阶段完成检查覆盖选择结果及其引用产物；不允许缺失 selected 时悄悄改用 raw。

验收：测试小于 1 → 1、1 → 小于 1、修改 seed、删除 selected fragment、选择零记录等情况；selected 分子数、支持 reads 总和及矩阵总和可核对。

## M2：QC、存储、配置和文库流程

### F04：quick-test 与正式处理共用有效性判定

- 复用同一 read 提取/纠错判定，要求所有必需片段完整且满足配置约定；统一 UMI、annotation 和 sequence-only 分支。
- quick-test 继续默认读取前 N 对 records，明确它是前缀诊断，不代表随机总体。
- 默认报告 QC，不把函数正常返回解释为生物学质量合格。提供显式的可配置失败阈值，启用阈值后才据此阻止正式流程。
- 输出过滤原因，包括提取失败、barcode 歧义、缺失 annotation、无效 UMI；保留分段诊断与整 read 统计的区别。

验收：对同一个小数据集，quick-test 与正式处理在有效 reads 及失败原因上逐条一致；部分 PB、FB、UMI 失败及零有效 reads 均覆盖。

### F05：统一 Parquet 数据集约定

- 建立集中读写/识别/校验接口，支持单文件和 fragment directory；去除业务模块中的重复 `is_file()`/后缀/旧 TSV 路径推断。
- 每种表使用明确 schema，计数为整数；空表也写出有 schema 的可读 Parquet，区分“零记录完成”与“不完整/缺失”。
- 报告能够读取 directory trace；注释缺口按完整多段 FB 计数。trace 关闭时，纠错阶段直接产出紧凑 annotation QC，避免依赖恢复不了的 trace。
- 新生成的 2.0 产物采用统一格式。旧 TSV 通过显式兼容读取或迁移支持，来源及能力限制必须可见。

验收：单文件、目录、多 fragment、空表、trace 开/关、多段 FB 得到一致可解释的统计；旧 TSV 迁移前后计数一致。

### F06：配置生效与阶段计划

- 将配置解析结果规范化并验证，再生成阶段计划。明确落实 `downsample.enabled` 和 `resume.enabled`；未知配置项、负距离、错误白名单长度、名称/输出列冲突应清晰报错。
- `downsample.enabled: false` 时不生成降采样任务，报告展示全深度结果且标明未做降采样；不存在伪造的 selected 指标。
- `resume.enabled: false` 时不加载批次恢复状态、不复用已有完成结果，按重算路径执行；仍记录新的完成状态与审计信息。
- 普通文库和 PI-seq 使用各自输入明细形成矩阵与报告；PB–CB 汇总基于 mapping 产物，不依赖未生成的 raw matrix summary。
- PB–CB 的降采样只生成需要的诊断，不意外生成 PB×CB selected 矩阵。
- PB–CB 分别记录 molecule support 与 read support，公开 dominance 当前按 read support 计算。测试 CB alias 合并后共享 UMI 的计数；若输出定义为最终 PB–CB–UMI 分子数，需再次合并重复分子并保留 reads 总和。

验收：三类文库端到端运行、独立阶段命令、重复运行、禁用降采样、禁用恢复、多样本汇总均通过；所有公开配置项有明确作用或显式弃用提示。

## M3：性能与分析策略

### F07：纳入 2.0 的保守性能修复

- barcode 原位置 exact 命中立即返回；维持已有候选评分及歧义规则。
- 矩阵汇总和导出改为 SQL 聚合/分批读取，避免将全部非零项 `fetchall()` 到 Python；DuckDB 的线程、内存和临时目录应有明确设置。
- 控制每次多样本汇总的发布次数，避免在循环内反复重写整个 workbook。
- 记录 UMI 超大分组及最大 component 的内存风险，不能声称 batch size 是所有情况下的硬内存上限。超预算要给出可定位原因，不能随意拆开有纠错关系的 UMI。

验收：优化前后纠错结果和矩阵计数一致；至少记录合成数据、四个 fixture 及一个百万级以上代表数据的耗时、峰值 RSS、临时磁盘峰值。速度改善根据测量报告，不承诺未经测量的倍数。

### A01：linker 候选策略验证

对比现有最短间隔规则与“先筛选预期长度、再考虑文库位置和匹配证据”的策略。重点比较错误定位、歧义率、fixed 回退率和最终计数，而非只比较提取成功率。

若真值和真实样本差异审查均通过，可将新策略纳入 2.0 并记录配置/算法版本；否则保留显式 legacy 策略及已知局限，将默认规则调整推迟到后续版本。不得无提示修改默认规则。

### A02：降采样解释与计算改进

- 2.0 必须将选择结果描述为明确 criterion 下的 selected ratio；历史字段名若继续保留，应说明它不是最佳测序深度的验证结论。
- 多 repeat 保留全部结果；曲线按 ratio 汇总均值和波动，不直接从所有 repeat 中挑最高值。选中 repeat 必须有固定规则，并能复现实际 selected 明细。
- 评估支持数直方图的解析曲线。对于支持数为 n 的分子，检出概率为 `1-(1-p)^n`，singleton 概率为 `n*p*(1-p)^(n-1)`。期望计数与实际随机样本分开存储；比值的期望不能用期望计数之比冒充。
- 原始 UMI 支持数抽样后重新聚类、重新 PI 过滤属于完整深度模拟，作为后续研究功能，不要求 2.0 实现。

不阻塞 2.0 的后续优化：大白名单邻居索引、质量值参与纠错、UMI 超大组完整解决方案、PB–CB dominance 新默认策略、新的测序深度推荐目标。

## M4：2.0.0 候选版本与发布

### 版本与兼容性

1. 基础修复完成后进入 `2.0.0rc1`；发现问题继续 `rc2` 等，满足发布条件后再改为 `2.0.0`。
2. 统一版本来源，避免 `__init__.py`、pyproject、setup shim 和测试分别硬编码版本；CLI、日志和构建包版本一致。
3. 更新 README/CHANGELOG 中“所有修改只升 patch”的历史约定，解释本次主要版本用于配置、完成状态与数据接口的变化。
4. 固定发布支持的 Python/平台与依赖测试范围。当前最低 Python 声明为 3.9；保留它必须验证，提升最低版本必须写入迁移说明。记录测试过的 Cutadapt、UMI-tools、PyArrow、DuckDB、GNU sort 版本。
5. 迁移文档列出配置转换、目录/表格式、指标命名、selected/full-depth、checkpoint 失效及必须重算的情况。旧结果不得仅改 `.done` 后继续使用。

## 第一批实施任务

第一批只处理 F01、F02、F03：阶段指纹与下游失效、可靠的阶段完成/恢复、selected 产物引用。先添加故障与重跑回归，再修改实现。

第二批处理 F04–F06，形成一致的 QC、存储和文库接口；第三批处理 F07 和分析策略验证，随后进入候选发布。每一批完成时记录实现项、验证证据、结果差异和剩余问题，避免把 2.0.0 变成没有收尾边界的整体重写。
